BURN-38 WebView2 context-loss repro on Windows / Intel Iris Xe, run 2026-11-05.
aria-burn-core main at e092993 (bench code as at 85d07d7) · aria-burn main at 9232a1a (debug build)
Windows 11 Home 26H2 (10.0.26300.9818) · Edge 156.0.4314.58 · WebView2 Runtime 156.0.4314.58 (registry;
the 156.0.4314.50 folder is also still installed) · all binaries x64
GPU Intel Iris Xe Graphics (0x9A49), driver 30.0.101.1191, ANGLE / Direct3D 11 · 16 GB RAM, on AC power
Bench server `npx vite bench --port 5299 --strictPort`. Each WebView2 run is a fresh aria-burn process on the
logged-in desktop, foreground, ARIA_BURN_BENCH_URL=http://localhost:5299/?auto=tiles,stages (runs 1-3) or
?auto=stages (run 4). Edge: fresh profile, same URL. Memory: Get-Counter "\GPU Adapter Memory(*)\Shared Usage"
(total) and "\GPU Process Memory(*)\Shared Usage" (largest process), plus free RAM, sampled every ~3.5 s.
Machine: the laptop's Claude app (~6 GB) and WSL (~7 GB, incl. the Plane server) stayed open; ~6.5-7 GB RAM
free before each run. No other build, test or bench ran.

Summary
- Reproduces 3 of 3 with ?auto=tiles,stages in WebView2. All pool steps allocate (up to 9000², 1313 MiB, alone
  and beside the 4096² overview), then the 5 µm job loses the context inside GlSim.fit()'s thermal step
  ("WebGL context lost before the thermal result was read back"), with only 794 MiB resident per the ledger.
  The context is not restored, so ?auto=stages in the same process stops at once.
- It is not caused by the pool churn: run 4, ?auto=stages alone in a fresh WebView2 process (no pool steps),
  lost the context twice: once after the fluence-only full run (restored), then in "upload bins" right after
  a 12.2 s thermal step (gl error 37442, not restored). BURN-36 recorded this sequence as passing.
- Every loss came when the WebView2 GPU process reached ~2.37 GB of shared GPU memory, while the bench's
  ledger counted 0.7-0.8 GB resident; free RAM was still 0.8-1.8 GB:
    run 1  WebView2 GPU process 2371 MiB (adapter total 2916 MiB), 1768 MiB RAM free  -> lost
    run 2  2371 MiB (2932), 1619 -> 1021 MiB free                                    -> lost
    run 3  2370 MiB (2917), 1649 -> 755 MiB free                                     -> lost
    run 4  1387 MiB at the first loss (930 MiB free), 2377 MiB (2939) at the second, 1617 MiB free
  The same ~2.37 GB level ended the BURN-41 detail runs (2374, 2374 MiB) and the BURN-35 5 µm live run
  (2519 MiB): burn-41-detail-tauri-windows-irisxe.txt, burn-35-live-tauri-windows-irisxe.txt.
- Edge passes the same ?auto=tiles,stages on the same machine (run 5): 5 µm job renders without context loss,
  forced-failure fallback and context-loss recovery PASS, both stage cases "all steps ok". Its GPU process
  went to 3712 MiB shared (adapter total 4260 MiB) with free RAM down to 565 MiB.
- No Display event 4101 (no TDR) and no low-memory event 2004 in the System log during any run.

Reading: the loss is WebView2-specific and tracks the GPU process's shared GPU memory (~2.37 GB), not the
pool allocate/free churn and not free RAM. The ledger's resident figure is ~1.6 GB below what the process
holds, so ANGLE / D3D11 keeps a large share outside the counted textures and buffers (staging or shadow
copies of the big per-sample buffers are the likely part). The app can hit it: the BURN-41 bench's app
sequence (fit, then full run) of the 5 µm 100 mm job with birch at the 50 M budget died the same way.
Pause / gl.finish() after frees was not tried: with no churn needed, it does not address this trigger.
No sim code changed.
