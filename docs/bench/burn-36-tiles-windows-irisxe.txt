BURN-36 tile-budget bench on Windows / Intel Iris Xe, run 2026-11-03, branch burn-36 at f6f8285.
Windows 11 Home 10.0.26300 · Edge 156.0.4314.58 · WebView2 Runtime 156.0.4314.58
GPU Intel Iris Xe Graphics (0x9A49), ANGLE / Direct3D 11. Reports copied from the `pnpm bench` log.
Each run was in a fresh process: Edge with a new --user-data-dir, WebView2 by restarting aria-burn
(debug build at 9ee8c33, ARIA_BURN_BENCH_URL pointed at this repo's bench page).

Summary
- Pool step: every full TargetSet allocated, up to 9000² (1313 MiB) alone and beside a 4096² overview
  (1756 MiB resident), in both Edge and WebView2. The size limit inferred in BURN-33 (~615–767 MB per
  pool) does not exist: 6711² pools (the BURN-33 0x8cdd size) allocate fine.
- WebView2, 5 µm job via fit() at the 768 MiB budget: with ~792 MiB of per-sample data resident, even a
  993×995 pool fails with 0x8cdd and the context is lost (37442). Every later case failed because of
  that. Edge passed the same sequence. Not explained by pool size; the per-sample buffers are the suspect.
- Tile size vs speed (Edge, 5 µm job): 768 MiB budget → 21 × 21 tiles ≤ 995, first 10.1 s / second 6.9 s.
  1536 MiB budget → 3 × 3 tiles ≤ 6720, first 31.7 s / second 20.5 s. Bigger tiles are ~3× slower here.
  GPU_BUDGET_BYTES left at 768 MiB pending that decision.
- ?auto=live in a fresh WebView2 process: the BURN-33 failure at the first spike-job refresh
  (6010 × 614 tile) does not reproduce on burn-36. All three cases ran, gl error 0. But the 5 µm live job
  reaches 210 tiles with a 10.3 s last refresh, and the thermal spike job's setup takes 1.2–3.0 s per refresh.
