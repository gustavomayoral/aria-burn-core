BURN-38: where the WebView2 GPU process's memory went, and the fix. Windows / Intel Iris Xe, run 2026-11-05.
Windows 11 Home 26H2 (10.0.26300.9818) · WebView2 Runtime and Edge 156.0.4314.58 · Iris Xe (0x9A49), driver
30.0.101.1191, ANGLE / Direct3D 11 · 16 GB RAM, on AC power. aria-burn main 9232a1a (debug build, unchanged).
Bench: ?auto=gpumem (bench/bench.ts runGpuMem, new in BURN-38) in a fresh aria-burn (WebView2) process each run.
Each step allocates or frees one thing, then waits 3-4 s; it POSTs a mark to the bench server, which logs it with
the laptop's clock. A sampler on the laptop read "\GPU Process Memory(*)\Shared Usage" for the browser GPU
process (msedgewebview2.exe) once a second. "at rest" = the last reading before the next step; "peak" = the
highest reading while the step ran. "ledger" = what the core's BURN-36 GPU byte ledger counted. MiB throughout.
6.5-7.8 GB RAM free before every run (the laptop's Claude app and WSL stay open, ~11 GB).

SUMMARY
- The GPU byte budget (BURN-36) counted textures and buffers at their size. On ANGLE / D3D11 that is right for
  textures and wrong for vertex buffers, and the per-sample buffers are the big ones (19.7 M samples for the 5 µm
  100 mm job: samples 225, bins 300, thermal statics 225):
    STATIC_DRAW vertex buffer  2x its size once drawn from (ANGLE keeps a staging copy beside the GPU buffer)
    DYNAMIC_DRAW vertex buffer not bound directly: each draw streams the range it reads into a streaming buffer
                               that the driver renames under load. The thermal step (~3000 draws over all 19.7 M
                               samples and their statics) took the process ~1.1 GB above its resting size.
    texture                    1x at rest; ~2x for a moment on first use (WebGL zero-initialises it)
    any free                   returned seconds later, not at once
- The 5 µm job's app sequence (thermal step, bins, overview, full run) took the WebView2 GPU process to
  2.4-3.2 GB while the ledger counted 0.4-1.1 GB. The earlier runs lost the context there.
- Fix (aria-burn-core burn-38): per-sample vertex data goes through bounded vertex windows
  (src/sim/gl/vertex-window.ts): one STATIC_DRAW buffer of up to 2 M items per array, refilled from the CPU
  array as draws walk it (bins by bucket row, the thermal step by time bin, coarse runs by checkpoint). The
  thermal step no longer keeps a whole-job statics buffer. Windows are used on ANGLE / Direct3D and on Intel
  renderers; elsewhere (M1) samples and bins stay whole buffers as before. The overview is cleared when it is
  allocated, so its first-use spike lands before the run's other data is on the GPU. Results are unchanged bit
  for bit (burn-38-fix-macos-m1.txt).
- After the fix the same sequence peaks at 1.25-1.4 GB at rest, ~1.8 GB for a moment (the overview's first
  use, at the start of fit), with the thermal step at 476.

WHAT THE BUDGET NOW SEES
The ledger counts the windows (24 MiB samples, 24 + 8 MiB bins, 24 + 24 MiB thermal step on Iris Xe) instead of
225 + 300 + 225 MiB of whole buffers. fit plans its tiles with what is really resident, so on Iris Xe the 5 µm
job (k = 1) now runs 121 tiles <= 1862 instead of 441 tiles <= 995 at the same 768 MiB budget.

WHAT IS LEFT
- The overview costs ~1.75x its ledger size once used (774 vs 442), and any big texture briefly ~2x on first
  use. Not counted by the ledger; with the per-sample data windowed it no longer matters for the 5 µm job.
- releaseTargets() followed at once by new allocations (the BURN-37 bench sequence in ?auto=detail) overlaps
  the old memory, which is freed seconds late, with the new: ~1.9-2.0 GB for a moment. The app releases on job
  close, before a new job is sampled, so its frees land first.
