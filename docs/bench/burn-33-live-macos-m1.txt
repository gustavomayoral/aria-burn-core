BURN-33 live-job benchmark — `pnpm bench`, button "Live job (BURN-33)" (window.__runLive()), run 2026-11-03
on this Mac in the Claude desktop app's Chromium (ANGLE/Metal, Apple M1), with the browser
pane hidden (background page). NOT the Tauri WKWebView and NOT Windows/Iris Xe.

What one refresh is: the app's live refresh (aria-burn src/lib/burn.svelte.ts scheduleLive → tick).
New batches arrive, the setup is rebuilt on live tiling, then a coarse run at the live head.
For a thermal material the coarse run reruns the whole thermal step, because the store changed.
The app waits max(100 ms, 2 × last refresh) before the next one. The job is fed in 10 equal chunks.

Reading it:
- The thermal step is almost the whole refresh. Without it a refresh is ~30 ms and the app
  refreshes at its 100 ms floor. With it, a refresh grows with the streamed job to ~2–3 s, so
  the view updates only every ~4–6 s by the end of a 100 mm job, on an M1.
- Run-to-run noise is large with the pane hidden: an earlier run of the same spike case had
  the thermal step at 0.63–1.0 s per refresh (median refresh 859 ms). Repeat in a visible
  pane, the Tauri webview, and on Windows/Iris Xe before deciding on a fix.
- Setup (live tiling) and the coarse run itself stay cheap: under 1 ms and under 90 ms.
- Candidate fix (from BURN-33's list): an incremental thermal step for live jobs, so a refresh
  costs the new samples, not the whole job so far.

Also fixed while adding this case: GlSim.releaseTargets() left lastFbo pointing at a deleted
framebuffer, so a sync() before the next run raised INVALID_OPERATION (1282) on bindFramebuffer,
readBuffer and readPixels. It showed as "gl error: 1282" when a fluence-only job followed a
thermal one.
